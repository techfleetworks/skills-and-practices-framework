# Schema

This folder holds the machine-readable contracts for the framework. It exists so other
software and AI systems can understand the data, while the framework keeps its own names.

The guiding rule: **our names stay the names.** A Job Function is still a `Job Function`; a
deliverable's description is still `Deliverable Description`. The universal vocabularies are
mapped *onto* our names, never over them.

## What is here

- **`context.jsonld`** — the crosswalk. It maps each of our field names and types to a
  standard meaning: to [schema.org](https://schema.org) where a good match exists, to
  [SKOS](https://www.w3.org/2004/02/skos/) (the W3C standard for vocabularies) for the
  concept structure, and to our own namespace (`spf:`) for everything the standards do not
  cover. This is what lets a machine read our `Job Function` as a `schema:Occupation` without
  us renaming anything.

- **`framework-data/*.schema.json`** — a JSON Schema for each entity. This is the shape
  contract: which fields exist, their types, and the `{slug, label}` form of every
  relationship. Generated by `tools/build-schemas.mjs`.

## How the standards are applied

- Every record is typed three ways at once: our own type (for example `spf:Deliverable`), the
  closest schema.org type (`schema:CreativeWork`), and `skos:Concept`. The framework as a whole
  is a set of `skos:ConceptScheme`s.
- Types are mapped like this: job functions and specializations to `schema:Occupation`, tools
  to `schema:SoftwareApplication`, activities, workshops, and methodologies to `schema:HowTo`,
  deliverables to `schema:CreativeWork`, and the rest to `schema:DefinedTerm`.
- Common properties map to schema.org (`name`, `description`, `url`, `competencyRequired`).
  Everything specific to this framework uses the `spf:` namespace, keyed by our exact field
  name.

## The machine-readable data

The JSON-LD view of the data lives in `data/jsonld/`. Each file keeps our exact field names as
its keys and references `context.jsonld`, so a standards-aware reader resolves them to
schema.org and SKOS automatically.

## Checking the data

`tools/validate.mjs` verifies that every record has a slug and that every relationship points at
a row that actually exists. Run it with `node tools/validate.mjs`; it is meant to run in CI so a
broken reference never ships.
